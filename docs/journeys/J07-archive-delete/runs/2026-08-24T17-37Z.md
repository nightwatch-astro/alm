and P2 (real files under a registered library root) were never established,
because the app could not be driven at all. No fixture was created and no

The app itself came up. `desktop_shell.exe` from the host checkout
(`a52c637f2`, working tree clean apart from untracked helper scripts) ran on
the Windows console session 1 with the real backend and a disposable database
(`PV_DB_URL=sqlite://C:\dev\astro-plan\wizard-test.db?mode=rwc`). The MCP

OF 8". So observation at UI fidelity worked.

Interaction did not. Every `execute_js` call returned
`Script execution timeout`, including `1+1`. Cause, read from the plugin
source rather than inferred: on non-macOS the command takes the
`eval_with_ipc_callback` path, and the script it injects returns its result
only through `window.__TAURI__.core.invoke` or `window.__TAURI__.event.emit`
(`tauri-plugin-mcp-bridge-0.11.2/src/commands/execute_js.rs:248-266`). With
neither present it logs `[MCP] __TAURI__ not available, cannot send result`
and the oneshot never resolves, so the 5 s timeout at `execute_js.rs:298-311`
fires. `window.__TAURI__` exists only when `withGlobalTauri` is set, which
the tracked `apps/desktop/src-tauri/tauri.conf.json` does not set — it is
supplied by the `tauri.dev.conf.json` overlay, and the binary under test was
built without it.

`execute_js` is the only interaction primitive the bridge exposes: the plugin
has no click, type, or key command, and the MCP server drives the DOM through
JS. So with `execute_js` down, no step of this journey is performable.
